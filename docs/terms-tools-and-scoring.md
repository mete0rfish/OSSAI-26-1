# 수업 도구·채점기·용어

이 문서는 Week 1–6에서 반복해서 쓰는 이름을 한 곳에서 설명한다. 실습 문서에서는 한국어
이름을 먼저 쓰고, 코드에서 찾을 영문 이름을 괄호에 함께 적는다.

## 한 사례가 처리되는 순서

```text
페이지 이미지 + 질문
→ 작업 모델(task model)
→ 원응답(raw response)
→ 출력 형식(schema) 검사
→ 고정 규칙 채점기(deterministic scorer)
→ 사례별 점수와 통과 여부
```

Week 3부터 필요한 경우에만 모델 기반 채점기(LLM judge)를 더한다. 정답 문자열, 숫자,
JSON 필드처럼 코드로 확인할 수 있는 항목은 모델 기반 채점기에 맡기지 않는다.

수업 명령이고, `src/verifiable_ai_workflow/`는 그 명령이 재사용하는 실제 구현이다.

## 고정 규칙 채점기와 평가지표

고정 규칙 채점기(deterministic scorer)는 같은 입력에 항상 같은 점수를 내는 Python
함수다. `evaluation/scoring.py`가 모델의 답을 다음 지표(metric)로 계산한다.

### 통과 여부를 정하는 필수 지표

| 코드 이름 | 한국어 뜻 | 1점 조건 |
| --- | --- | --- |
| `schema_validity` | 출력 형식 유효성 | JSON이 정해진 필드와 자료형을 만족한다. |
| `abstention_correct` | 답변 보류 정확성 | 답이 없을 때만 보류했고, 답이 있을 때는 보류하지 않았다. |
| `answer_correct` | 정답 허용 기준 | 숫자·문자 유사도 등 사례 유형별 기준을 만족한다. |
| `evidence_coverage` | 근거 페이지 포함 | 허용된 근거 페이지를 하나 이상 제시했다. |
| `task_success` | 전체 성공 | 위 네 지표가 모두 1점이다. |

`task_success`만 최종 통과·실패를 결정한다. 평균 점수가 높아도 필수 조건 하나가 0이면 그
사례는 실패다.

### 실패 원인을 읽는 진단 지표

| 코드 이름 | 한국어 뜻 | 무엇을 확인하는가 |
| --- | --- | --- |
| `json_object_only` | JSON 단독 반환 | 코드 블록이나 설명 없이 JSON만 반환했는가 |
| `answer_exact` | 정답 완전 일치 | 공백·기호를 정리한 답이 기대 답과 같은가 |
| `answer_similarity` | 문자 유사도 | 정리한 두 문자열이 얼마나 비슷한가 |
| `answer_anls` | 편집거리 기반 유사도(ANLS) | 문서 질의응답에서 오탈자를 얼마나 허용할지 보는가 |
| `answer_token_f1` | 답 토큰 F1 | 두 답의 단어·숫자 겹침이 정밀도와 재현율 면에서 어떤가 |
| `numeric_match` | 숫자 일치 | 기대한 숫자 목록과 반환한 숫자 목록이 같은가 |
| `evidence_page_precision` | 근거 페이지 정밀도 | 제시한 페이지 중 정답 페이지 비율은 얼마인가 |
| `evidence_page_recall` | 근거 페이지 재현율 | 기대한 페이지 중 찾아낸 비율은 얼마인가 |
| `evidence_page_f1` | 근거 페이지 F1 | 페이지 정밀도와 재현율의 조화평균은 얼마인가 |
| `quote_answer_support` | 인용문·답 자체 일관성 | 모델이 쓴 인용문에 모델 답의 핵심값이 있는가 |

F1은 두 비율을 한 값으로 요약할 때 쓴다. 한쪽만 높고 다른 쪽이 낮으면 F1도 낮아진다.
`answer_token_f1`은 짧은 텍스트 답의 겹침, `evidence_page_f1`은 페이지 집합의 겹침을 본다.
VQA에서 답과 근거를 빠르게 진단하는 보조값이며 최종 통과 조건은 아니다.

`quote_answer_support`는 모델이 작성한 두 필드가 서로 맞는지만 본다. 인용문이 실제 이미지에
있는지는 증명하지 않으므로 독립적인 근거 사실성 점수로 해석하지 않는다.

## 모델 기반 채점기

모델 기반 채점기(LLM judge)는 정답 표현이 다양해 고정 규칙만으로 판정하기 어려울 때 다른
모델에 평가를 요청한다. 호출할 때마다 판단이 달라질 수 있어 확률적 채점기(stochastic
scorer)라고도 한다.

Week 1–2 AIHub 실습은 짧은 정답과 페이지 번호가 있어 고정 규칙 채점기를 사용한다.
Week 3 OpenCQA처럼 긴 설명 답을 비교할 때 모델 기반 채점기를 추가하고, 사람 라벨과 먼저
맞춰 본 뒤 사용한다.

## 실행과 결과 용어

| 한국어 이름 | 코드 이름 | 뜻 |
| --- | --- | --- |
| API 제공자 | provider | 모델 API를 운영하는 서비스 |
| 호출 경로 | route | 제공자·모델·접속 주소를 묶은 호출 대상 |
| 소규모 사전 실행 | probe | 전체 실행 전에 1–3건으로 입력·출력·오류를 확인하는 실행 |
| 실행 | run | 고정한 데이터·모델·지시문으로 묶어 수행한 한 번의 평가 |
| 실행 식별자 | `run_id` | 서로 다른 실행 결과 폴더를 구분하는 이름 |
| 반복 식별자 | `trial_id` | 같은 조건의 반복 호출을 구분하는 이름 |
| 저장 응답 | fixture | API 없이 파서와 채점기를 반복 검사하는 고정 응답 |
| 재실행 | replay | 저장 응답을 다시 읽어 같은 코드를 실행하는 것 |
| 결과 파일 | artifact | 원응답, 점수, 요약처럼 실행 뒤 남는 파일 |
| 통과 조건 | gate | 후보를 채택하려면 반드시 만족해야 하는 규칙 |

`passed`는 필수 지표 통과, `failed`는 정상 응답이 채점 기준 실패,
`inconclusive`는 API 오류나 모델 불일치로 품질을 판정할 수 없음을 뜻한다. 오류를 오답으로
바꾸면 모델 품질과 서비스 가용성을 혼동하므로 세 상태를 분리한다.

시험 전용 증거(`test_only`)는 저장 응답·모의 응답으로 코드만 확인한 결과다. 실제 품질 증거
(`live_quality`)는 대체 경로와 재실행을 끄고 실제 API 응답을 채점한 결과다. 가용성 증거
(`availability`)는 대체 경로를 포함해 서비스가 응답을 이어 갈 수 있는지를 본다.
