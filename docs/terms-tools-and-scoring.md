# 수업 도구·채점기·용어

이 문서는 Week 1–6에서 반복해서 사용하는 용어를 한 곳에 모아 설명한다. 실습 문서에서는
한국어 이름을 먼저 쓰고, 코드에서 찾을 영문 이름을 괄호에 함께 적는다.

## 한 사례가 처리되는 순서

```text
페이지 이미지 + 질문
→ 작업 모델(task model)
→ 원응답(raw response)
→ 출력 형식(schema) 검사
→ 고정 규칙 채점기(deterministic scorer)
→ 사례별 점수와 통과 여부
```

Week 3부터 필요한 경우에만 모델 기반 채점기(LLM judge)를 더한다. 정답 문자열, 숫자,
JSON 필드처럼 코드로 확인할 수 있는 항목은 모델 기반 채점기에 맡기지 않는다.

| 이름 | 수업에서 하는 일 | 처음 사용하는 곳 |
| --- | --- | --- |
| `uv` | Python 버전·패키지·실행 명령을 같은 `uv.lock` 기준으로 맞춘다. | 환경 준비 |
| LiteLLM | NVIDIA NIM과 Gemini를 같은 Python 호출 형태로 연결한다. | Week 1 |
| Pydantic v2 | 모델 JSON을 `answer`, `abstained`, `evidence` 필드로 검사한다. | Week 1 |
| JSON Schema | 허용하는 출력 필드와 자료형을 문서화한다. | Week 1 |
| DeepEval OSS | 이미 계산한 사례별 지표를 한 실행 결과로 묶어 탐색한다. 이 저장소의 정답 판정식을 대신하지 않는다. | Week 1 |
| pypdfium2·Pillow | PDF 각 쪽을 VLM 입력용 JPEG로 만든다. | Week 1 |

라이브러리는 설치해 사용하는 기능 묶음이다. `scripts/`에는 학습자용 분석 명령과 Week 2–4 개인
전체 실행 명령, 튜터의 자료 준비·대표 live 명령이 있고, `src/verifiable_ai_workflow/`에는 이 명령들이
재사용하는 실제 구현이 있다. 누가 어떤 명령을 실행하는지는 주차 실습서와 튜터 runbook에서
구분한다.

## 고정 규칙 채점기와 평가지표

고정 규칙 채점기(deterministic scorer)는 같은 입력에 항상 같은 점수를 내는 Python
함수다. `evaluation/scoring.py`는 모델의 답을 다음 지표(metric)에 따라 계산한다.

### 통과 여부를 정하는 필수 지표

| 코드 이름 | 한국어 뜻 | 1점 조건 |
| --- | --- | --- |
| `schema_validity` | 출력 형식 유효성 | JSON이 정해진 필드와 자료형을 만족한다. |
| `abstention_correct` | 답변 보류 정확성 | 답이 없을 때만 보류했고 답이 있을 때는 보류하지 않았다. |
| `answer_correct` | 정답 허용 기준 | 기준 답 또는 데이터에 명시한 허용답과 정규화 완전일치한다. |
| `evidence_coverage` | 근거 페이지 포함 | 허용된 근거 페이지를 하나 이상 제시했다. |
| `task_success` | 전체 성공 | 위 네 지표가 모두 1점이다. |

`task_success`만 최종 통과·실패를 결정한다. 평균 점수가 높아도 필수 조건 중 하나가 0이면
그 사례는 실패다.

### 실패 원인을 읽는 진단 지표

| 코드 이름 | 한국어 뜻 | 무엇을 확인하는가 |
| --- | --- | --- |
| `json_object_only` | JSON 단독 반환 | 코드 블록이나 설명 없이 JSON만 반환했는가 |
| `answer_exact` | 정답 완전 일치 | 공백·기호를 정리한 답이 기대 답과 같은가 |
| `answer_similarity` | 문자 유사도 | 정리한 두 문자열이 얼마나 비슷한가 |
| `numeric_match` | 숫자 일치 | 기대한 숫자 목록과 반환한 숫자 목록이 같은가 |
| `quote_answer_support` | 인용문·답 자체 일관성 | 모델이 쓴 인용문에 모델 답의 핵심값이 있는가 |

Week 1–2에서는 위 다섯 진단값만 사용한다. ANLS와 token·페이지 F1은 최종 판정에 쓰이지 않는
데다 학습할 지표만 늘리므로 제외했다. 다른 VQA 데이터셋의 공식 평가 계약이 요구할 때만 그
데이터셋 실습에 추가한다.

`quote_answer_support`는 모델이 작성한 두 필드가 서로 맞는지만 본다. 인용문이 실제 이미지에
있는지는 확인하지 않으므로 독립적인 근거 사실성 점수로 해석하지 않는다. 실제 근거를
검증하려면 사람이 JPEG를 대조하거나 별도의 이미지 근거 검사 절차를 거쳐야 한다.

## 모델 기반 채점기

모델 기반 채점기(LLM judge)는 정답 표현이 다양해 고정 규칙만으로 판정하기 어려울 때 다른
모델에 평가를 요청한다. 호출할 때마다 판단이 달라질 수 있으므로 확률적 채점기(stochastic
scorer)라고도 한다.

Week 1–2 AIHub 실습은 짧은 정답과 페이지 번호가 있어 고정 규칙 채점기를 사용한다.
Week 2에서 각 학습자는 동일 release baseline을 기준으로 자기 prompt의 40건 결과를 만들고
계보가 같은지 확인한 뒤 비교한다. 저장된 개선·provider 결과는 설명 예시와 실패 fallback이다.
전체 절차와 결과 위치는 [Week 2 실습](week-02-lab.md)을 따른다.

Week 3 OpenCQA처럼 긴 설명 답에는 과정의 고정 4단계 기준을 사용한다. 이때 **작업 모델**은
NVIDIA NIM의 Gemma다. 같은 모델에 기준·개선 지시문을 적용해 차트 질문별 실제 답 두 개를
만든다. OpenCQA 사람이 쓴 `abstractive_answer`는 기대 답으로만 쓰며 후보에 넣지 않는다.

**Judge 모델**은 Google AI Studio의 Gemini 3.5 Flash Lite다. Gemini는 차트 이미지·질문·기대
답과 익명화한 Gemma 후보 A/B를 보고 상대 판단한다. 각 학습자는 Gemini 결과를 보기 전에
배정된 1쌍을 판단해 `human-label.yaml`에 기록하고 SHA-256을 동결한다. 그런 다음 같은 30쌍을
두 trial·A/B·B/A로 실행하고 `interpretation.md`에 순서·반복 충돌을 쓴다.

Prompt 최적화는 실제 실패 답을 보고 지시문을 고친 뒤, 별도 문제에서도 답이 좋아졌는지
확인하는 과정이다. Week 4에서 Gemini는 정답을 판정하지 않고 지시문을 고쳐 쓴다. NIM
Gemma가 차트 답을 만들면, Gemini는 이미지 없이 지시문·질문·기대 답·NIM 출력·고정 점수와
이유를 읽는다. 바꾼 지시문은
검증 문제 6개로 NIM Gemma에 다시 적용한다. 평균 점수가 처음 지시문보다 높지 않으면 처음
지시문을 그대로 쓴다.

Google 전송 범위는 2026-08-17에 승인됐다. 공식 Free Tier 근거는 15 RPM·입력 250,000 TPM·
500 RPD지만, 실행 전에는 현재 프로젝트의 실제 한도를 다시 확인한다. 수업 코드는 15 RPM·입력
75,000 TPM·출력 7,500 TPM과 한 full run당 최대 240요청을 적용한다. 하루 누적 요청은 추적하지
않으므로 실행 전 당일 잔여 RPD가 240건 이상인지 확인한다. 120~240회 요청은 pacing에만 약
8~16분이 걸린다. Free Tier token 단가는 0달러이고 0.01달러는 코드의 비용 안전장치다. Free
Tier 자료가 제품 개선에 쓰일 수 있다는 조건을 허용할 수 없으면 호출하지 않는다.

과거 OpenCQA `abstractive_answer / extractive_answer`와 NIM Gemma Judge를 비교한 Codex 합성
기준과 저장 결과는 legacy 수업 자료다. 새 개인 실행·사람 label·Gemini 결과의 기준이나 완료
근거로 쓰지 않는다. 한 사람의 한 판단은 `human_calibrated`가 아니다. 실제 사용 전에는 최소
30개 실제 업무 출력에 두 사람이 blind label을 작성하고 불일치를 조정하는 별도 절차를
권장한다. 이번 개인 실습은 `classroom_demo`이며 정식 사람 보정을 대신하지 않는다.

## 실행과 결과 용어

| 한국어 이름 | 코드 이름 | 뜻 |
| --- | --- | --- |
| API 제공자 | provider | 모델 API를 운영하는 서비스 |
| 호출 경로 | route | 제공자·모델·접속 주소를 묶은 호출 대상 |
| 소규모 사전 실행 | probe | 전체 실행 전에 1–3건으로 입력·출력·오류를 확인하는 실행 |
| 실행 | run | 고정한 데이터·모델·지시문으로 묶어 수행한 한 번의 평가 |
| 실행 식별자 | `run_id` | 서로 다른 실행 결과 폴더를 구분하는 이름 |
| 반복 식별자 | `trial_id` | 같은 조건의 반복 호출을 구분하는 이름 |
| 저장 응답 | fixture | API 없이 파서와 채점기를 반복 검사하는 고정 응답 |
| 재실행 | replay | 저장 응답을 다시 읽어 같은 코드를 실행하는 것 |
| 결과 파일 | artifact | 원응답, 점수, 요약처럼 실행 뒤 남는 파일 |
| 통과 조건 | gate | 후보를 채택하려면 반드시 만족해야 하는 규칙 |

`passed`는 필수 지표 통과를 뜻하고, `failed`는 정상 응답이 채점 기준을 통과하지 못했다는
뜻이다. `inconclusive`는 API 오류나 모델 불일치로 품질을 판정할 수 없는 상태다. 오류를
오답으로 바꾸면 모델 품질과 서비스 가용성을 혼동하므로 세 상태를 분리한다.

시험 전용 증거(`test_only`)는 Git 고정 응답·모의 응답·재실행으로 코드만 확인한 결과다.
실제 품질 증거(`live_quality`)는 대체 경로와 재실행을 끈 상태에서 실제 API 응답을 채점한
결과다. 실제 API 원본은 저장되어 있어도 `live_quality`다. 가용성 증거(`availability`)는
대체 경로를 포함해 서비스가 응답을 이어 갈 수 있는지를 본다.
